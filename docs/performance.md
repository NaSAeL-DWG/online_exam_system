# 100 人并发作答实测报告与复现指南

为了验证系统在真实班级集中考试场景下的稳定性与数据一致性，我们在本地单机环境下完成了 **3 轮、每轮 100 名学生同时在线作答（每份试卷 20 道客观题，每轮产生 2,000 条答题记录）** 的端到端 HTTP 压测验证。

> **结论先行**：三轮压测（涵盖错峰常态作答、100 人同秒峰值作答 + Worker 停机恢复、100 人到期自动收卷）共发出 **13,600 次考试业务 HTTP 请求，成功率 100%（零 5xx 错误、零网络传输失败）**，所有学生的提交状态、答案内容与最终判分 100% 准确一致。
> *注：本报告数据仅代表下述单机硬件与短时客观题工作负载下的实测表现，不直接等同于跨公网生产环境的容量承诺。*

## 一、实测硬件与软件环境

| 维度 | 实测配置详情 |
| :--- | :--- |
| **处理器与内存** | Windows 11 · Intel Core i7-14650HX（24 逻辑核心）· 约 15.61 GiB 物理内存 |
| **后端运行时** | Python 3.13.14 · FastAPI 0.117.1 · Uvicorn 0.36.0 |
| **数据库与缓存** | PostgreSQL 18.3 · Redis 8.8 |
| **服务进程拓扑** | 1 个 FastAPI 应用进程 + 1 个独立 ARQ Worker 进程 |
| **数据库连接池** | 每个进程 SQLAlchemy 基础连接池 `5`、最大溢出 `10`；PostgreSQL `max_connections=100` |
| **隔离测试目标** | 专用数据库 `exam_test_iteration6_load` · Redis DB `13` · 独立端口 `18001` · 每轮独立队列 |
| **累计落库规模** | 417 个账号、12 场考试、416 份有效答卷、8,064 条单题答案（数据库体积约 18.46 MiB） |

**测试准备与限流验证说明：**
- 每名模拟学生都拥有自己独立的账号、HttpOnly Cookie 会话、独立答卷和防多开页面令牌（Page Lease）。
- 账号创建与考前登录单独计时（每次最多 5 个并发登录，**不关闭系统的登录防爆破限流**）。我们还专门测试了用同 IP、同一不存在账号连续发起 12 次登录请求，每轮均精准返回 10 次 `401` 和 2 次 `429 Too Many Requests`，证明认证限流机制在压测期间全程有效。

## 二、三轮百人并发实测结果

在每轮测试中，100 名学生完整执行：**读取考试列表 → 查看考试详情 → 点击开始考试 → 激活作答页面租约 → 逐题保存 20 道答案 → 重新读取校验**。为了精确核对判分准确性，每轮固定安排 **50 人全部填正确答案（应得 50 分）、50 人全部填错误答案（应得 0 分）**。

| 压测轮次与场景设计 | 业务请求成功率 | 答题阶段总耗时 | 响应延迟 (p50 / p95 / p99) | 最终数据与判分一致性核对 |
| :--- | :---: | :---: | :---: | :--- |
| **场景 1：稳态错峰作答**<br>5 秒内错峰进场，每题思考 0.75~1.25 秒，Worker 全程常驻，手动交卷 | **4,600 / 4,600**<br>(100%) | 45.147 秒 | 318 ms / 764 ms / 1,025 ms | 100 人全部手动交卷成功，50 人满分、50 人零分，答案与得分 100% 吻合 |
| **场景 2：峰值同秒冲击 + Worker 故障恢复**<br>100 人同一秒开始、零思考连续保存交卷；期间暂停 Worker，全部交完卷后再启动 Worker | **4,600 / 4,600**<br>(100%) | 33.123 秒 | 687 ms / 1,222 ms / 1,549 ms | Worker 恢复前：100 份已交卷、0 份已判分（答案零丢失）；<br>Worker 启动后：**6.53 秒内**全部补判完成，分数 100% 吻合 |
| **场景 3：峰值保存 + 到期自动收卷**<br>100 人零思考答完 20 题但不点交卷；等 60 秒考试时间真实截止后，再启动 Worker | **4,400 / 4,400**<br>(100%) | 31.594 秒 | 692 ms / 1,243 ms / 1,568 ms | Worker 启动后：**5.55 秒内**将 100 份答卷全部自动标记为 `TIMEOUT` 收卷并判分完成，有效提交时间全部精确等于考试 `deadline` |

### 关键性能指标解读
1. **延迟表现**：峰值最高同时在途请求数为 100。在场景 1（模拟真实学生带思考间隔的稳态作答）下，整体请求 p95 延迟仅为 **763.7 ms**（低于 1 秒），其中涉及行级锁写入的“开始考试”和“激活租约”接口 p95 约为 `1,033 ms` / `1,015 ms`。
2. **故障恢复速度**：场景 2 和场景 3 中记录的 `6.53 秒` 和 `5.55 秒` 恢复窗口，包含了压测脚本发 HTTP 请求核对状态、拉起 Worker 子进程以及最终巡检确认的全部时间，实际纯 Worker 批处理耗时更短。
3. **进程资源占用**：稳态压测期间，后端 API 进程树内存（RSS）峰值约为 **131.56 MiB**，ARQ Worker 内存峰值约为 **92.05 MiB**，API 单核折算 CPU 峰值约 `106.5%`，资源开销非常轻量。

## 三、如何在你的机器上复现压测？

我们把整套并发验证逻辑封装成了开箱即用的脚本 `backend/scripts/verify_concurrency.py`。

### 1. 准备条件
1. 已安装后端依赖（`uv sync --locked --python 3.13`），且本机 PostgreSQL 和 Redis 正在运行。
2. 准备好 `.local/backend-test.env`（内含 `TEST_DATABASE_URL` 和 `TEST_REDIS_URL`，数据库账号需具备创建隔离测试库和执行迁移的权限，详见 **[测试与验证指南](testing.md)**）。

### 2. 依次运行验证命令
打开终端，在 `backend/` 目录下**按顺序串行执行**（运行期间请勿同时跑浏览器 E2E 测试或其他高负载任务）：

```bash
cd backend

# 0. 先做环境与配置自检
uv run python scripts/verify_concurrency.py --source-env ../.local/backend-test.env --check-only

# 1. 复现场景 1：100 人错峰稳态作答 + Worker 常驻
uv run python scripts/verify_concurrency.py --source-env ../.local/backend-test.env \
  --students 100 --questions 20 --mode steady --worker-policy running

# 2. 复现场景 2：100 人同秒峰值交卷 + Worker 停机后恢复补判
uv run python scripts/verify_concurrency.py --source-env ../.local/backend-test.env \
  --students 100 --questions 20 --mode peak --worker-policy recover

# 3. 复现场景 3：100 人不点交卷 + 等待 60 秒真实截止后自动超时收卷
uv run python scripts/verify_concurrency.py --source-env ../.local/backend-test.env \
  --students 100 --questions 20 --mode peak --worker-policy recover \
  --submission timeout --deadline-seconds 60
```

### 3. 安全机制与报告产物
- **绝不污染开发库**：压测脚本强制只接受本机地址、专用隔离库（`exam_test_iteration6_load`）和独立端口 `18001`，它会自动拉起和关闭专用的 API 与 Worker 进程，绝不会清空或触碰你的日常开发数据库。
- **报告去哪看**：每轮跑完后，详细的延迟百分位、请求明细和 CPU/内存采样数据会自动保存在 `.local/iteration6/load/` 目录下的 `summary.json` 中（因包含本地运行配置，该目录已被 Git 忽略，请勿直接提交）。

## 四、测试边界说明

本次实测聚焦于**短时高并发在线答题、逐题自动保存、手动/超时交卷以及后台 Worker 容灾恢复**。它尚未包含：100 人在同一毫秒瞬间点击登录、跨地域公网高延迟弱网模拟、长达数小时的挂机保持、超大图片并发加载以及大规模主观题人工同时打分。在正式生产服务器上线前，建议结合实际考场人数和服务器配置再次运行上述脚本进行摸底。
