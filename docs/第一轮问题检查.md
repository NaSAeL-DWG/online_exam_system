## 2. 问题明细

### R1-01：响应契约未与数据库模型彻底分离

证据：`backend/app/routes/auth.py:115–117` 返回 RegistrationReview 表模型；`backend/app/schemas.py:33–42` 已定义 ApplicationPublic，其他申请接口使用该响应模型。路由普遍未声明 response_model 或返回类型。

影响：返回字段依赖表模型，数据库字段增加可能无意扩大公开响应；相同业务对象在不同入口的返回形状不一致，OpenAPI 缺少明确的成功响应结构。当前不能据此断言已泄露密码等敏感数据。

依据：数据库表结构文档要求表模型、输入模型、响应模型分离。

处理方向：所有业务接口声明明确的响应模型；表对象只作为内部数据，经过显式映射再输出。不能通过响应模型配置任意允许额外字段来绕过该规则。

验证：注册、申请查询、重申使用一致申请 DTO；检查 OpenAPI 输出；确认数据库内部字段不会直接出现在响应中。

### R1-02：业务生命周期按角色拆散

证据：`routes/auth.py:81–110` 创建注册申请；`routes/student.py:57–85` 拒绝后重申；`routes/staff.py:55–79` 审核并激活；`routes/admin.py:136–151` 恢复账号时再次判断审核结果。

影响：同一个“申请—审核—激活—停用恢复”规则跨四个角色路由维护，同时各自组织用户／资料／申请和审计写入。调整状态规则时需要多处同步，容易遗漏某个入口。

性质：这是可维护性判断，原规范没有规定必须使用 Service 或 Repository，不能将不存在某个文件名判作违规。

处理方向：按业务模块集中注册审核和账号状态用例；保留角色化 URL，但入口调用同一业务规则。HTTP、CLI 等入口复用业务能力，不互相调用路由函数。

验证：既有注册、拒绝重申、通过、停用恢复行为保持一致；检查状态转换和审计是否有单一归属。

### R1-03：响应组装隐藏 N+1 查询

证据：`routes/classes.py:121–123` 遍历班级调用 `_class_public`；该函数 `43–60` 每次查询全部成员并构造学生摘要，即使 include_students 为 false。

影响：列表查询次数随班级数线性增长；只需要人数仍加载每个学生。响应映射函数包含数据库访问，使调用成本不明显。未测得性能数值，不宣称当前已经达到性能瓶颈。

处理方向：列表使用聚合人数与批量教师查询，详情再按需加载学生；响应转换不触发隐式 I/O。建立一致的分页约定，避免后续列表持续全量读取。

验证：多班级数据下验证结果与查询数量，数量不随班级数逐项增长；列表不构造用不到的学生详情。

### R1-04：认证模块未隐藏 Redis 操作顺序

证据：`routes/auth.py:129–147、163–201、221–290` 和 `routes/admin.py:172–178、213–216` 直接获取 Redis、编排会话操作并重复转换 RedisError。改密和改联系方式重复限流、验证当前密码、锁行和清理计数。`security.py` 同时实现密码哈希、JWT、会话和 Lua 限流。

影响：调用者仍需理解 Redis key、异常及操作顺序；认证策略变化会波及多个 HTTP 入口。问题在于调用方承担了策略，而不是因为 security.py 的行数或使用函数风格。

处理方向：集中会话存储与认证用例，路由仅处理 Cookie／HTTP 信息和调用结果。保留路由层通用流控；密码验证频率等业务敏感规则由业务能力统一使用，CLI 或其他入口不能无意绕过。

验证：普通业务路由不直接拼接 Redis key；同一认证策略从多个入口调用时行为一致；保留真实 Redis 集成测试。

### R1-05：提交后故障与业务成功语义冲突

证据：`routes/auth.py:243–248` 改密码先 commit，再清理 Redis，失败则返回 503；联系方式 `286–290` 同样如此。管理员停用／恢复 `routes/admin.py:168–178` 和重置 `212–216` 也具有该结构。

触发：数据库提交成功，紧随其后的 Redis 操作失败。调用方收到错误，但密码、资料、状态及审计已写入；使用旧密码重试改密会再次失败。

现有保障：`deps.py:56–60` 检查数据库状态和 auth_version，Redis 故障时认证失败关闭。不能把本问题描述为旧会话必然仍能访问。

处理方向：由顶层业务用例定义提交点及提交后的失败策略；数据库提交成功后，Redis 清理可重试并可观测，响应应准确表达业务已完成。可采用轻量持久补偿或适用的恢复机制，不能仅吞掉异常。无需为了这项整改直接引入分布式事务框架。

验证：在 commit 后注入 Redis 故障，检查最终数据库、旧会话访问、客户端响应及重试行为；恢复后完成清理且不重复写业务审计。

### R1-06：Refresh Token 消费早于数据库检查

证据：`routes/auth.py:166–177` 先 rotate_refresh，再查询数据库用户；`security.py:156–169` 已更新新 Token 摘要，旧 Token 重试不匹配时还会删除会话。

触发：Redis 轮换成功，后续数据库查询失败；浏览器未拿到新 Cookie，而旧凭据已经失效，再次刷新可能使会话被删除。

处理方向：将必要的用户查询和检查移到最终凭据消费前，统一封装轮换流程；明确版本校验、原子 CAS、失败及重试语义。调整顺序本身不能解决响应在网络中丢失的所有问题，应单独规定最终轮换后的交付失败行为，不承诺完全无感恢复。

验证：覆盖轮换前数据库故障、原子轮换竞争、停用／重置与刷新并发、旧 Token 重放，以及轮换成功但响应未交付的策略。既有正常轮换测试不能替代这些场景。

### R1-07：行锁不刷新 identity map 中的属性

证据：`deps.py:56` 将 User 载入当前 AsyncSession；`routes/auth.py:228–230、269–270` 再通过相同 Session 的 get(..., with_for_update=True) 获取同一用户，未指定 populate_existing。

验证边界：Luna 报告通过不访问项目数据库的 SQLAlchemy 隔离脚本确认，with_for_update 会执行锁查询，但已有对象属性仍可能保留旧值；populate_existing 才显式刷新。该隔离脚本未作为项目测试交付，真实 PostgreSQL 并发流程仍需补测。

风险场景：身份依赖读到旧用户后，另一事务重置密码或停用账号；当前请求锁行后仍根据旧密码／状态／auth_version 继续改密，可能覆盖新密码或丢失版本递增。

处理方向：在 CRUD 锁读取中明确刷新语义，在锁定业务事务中重新验证状态、身份版本和当前密码。身份依赖返回的对象不能替代关键写操作时的实时业务验证。

验证：用可控并发步骤覆盖“先读身份—管理员提交重置／停用—原请求继续写入”，验证旧身份不能覆盖新状态且版本单调推进。

## 3. 应保留的实现

- FastAPI lifespan 管理异步数据库／Redis 连接生命周期。
- Argon2 哈希移出事件循环。
- 当前数据库用户状态和 auth_version 对旧会话的约束。
- 大多数接口已使用独立 Pydantic 响应模型。
- 真实 PostgreSQL／Redis 的 HTTP 集成测试、迁移一致性和浏览器流程。
