# 系统日志与安全审计指南

**中文** | [English](logging.en.md)

激活状态的系统管理员可从左侧导航进入 **“系统日志”** （路径 `/admin/logs`），集中查看全站 **运行日志（Runtime Logs）** 与 **操作审计（Audit Logs）**。

> **权限边界**：普通教师、学生及未登录用户无权查看、下载日志或修改日志采集配置，所有筛选、设置与导出接口均由后端严格校验管理员权限。

---

## 一、怎么查日志？（筛选规则与实时跟随）

页面顶部可切换 **“运行日志”** 与 **“操作审计”** 两个视图：
- **运行日志**：支持按时间范围、所属模块、业务任务、关键词及请求/任务关联 ID（Correlation ID）过滤。
- **操作审计**：支持按操作人、操作类型、目标对象类型及对象 ID 过滤，专门追踪登录、改密、发考、改分、公布/撤回成绩等关键行为。

单条运行日志采用清晰的标准文本格式展示：

```text
2026-11-02T14:23:08.126+08:00 INFO: [exam](发布考试): 考试发布成功
```

### 重点注意：累加式等级筛选规则
本项目的日志等级筛选采用 **由少到多的“累加包含规则”**，而不是传统意义上的“只看某级别及更严重的错误”。切换等级下拉框时，实际显示的日志范围如下：

| 当你选择的等级是 | 列表实际展示的日志等级 | 适用场景 |
| :--- | :--- | :--- |
| **`INFO`** | 仅显示 **`INFO`** | 只看正常的业务流转关键节点 |
| **`WARNING`** | 显示 **`INFO` + `WARNING`** | 在正常业务流基础上，加上需要注意的预警信息 |
| **`ERROR`** | 显示 **`INFO` + `WARNING` + `ERROR`** | 排查报错时，同时保留前后的正常业务上下文，方便还原现场 |
| **`DEBUG`** | 显示 **全部已采集等级（含 `DEBUG`）** | 深度排查底层细节（需配合下方的“临时 DEBUG 采集”开关使用） |

### 实时刷新与浏览体验
- **自动跟随与翻阅暂停**：页面默认开启每 3 秒自动轮询刷新与底部跟随。当你往上滚动翻看历史日志时，页面会自动暂停滚动，防止新刷出来的日志把你正在看的行顶走；点一下 **“回到最新”** 即可恢复实时跟随。
- **内存与防乱序保护**：历史日志支持分页读取，前端会控制单页保留的最大行数，长时间开着日志页也不会卡死浏览器。快速切换筛选条件时，迟到的旧请求响应会被自动丢弃，绝不会覆盖最新筛选结果。
- **时区显示**：列表默认按你当前浏览器的本地时区展示时间；点击展开某条日志详情，或导出下载 `.log` 文件时，会保留服务器原始的带时区 ISO 时间戳（如 `+08:00`）。

## 二、开启 15 分钟临时 DEBUG 采集

平时为了避免海量的普通查询、列表轮询和后台空扫描把日志库塞满，系统默认只采集 `INFO`、`WARNING`、`ERROR` 级别的日志。你在筛选框里光选 `DEBUG` 只是放开了查看范围，如果当时没有开启采集，是看不到底层 `DEBUG` 细节的。

**当线上某个模块出现疑难杂症需要看详细参数和内部步骤时：**
1. 在系统日志页面的管理设置区，勾选需要排查的模块并开启 **“临时 DEBUG 采集”**。
2. 开启后，所有连接同一个数据库的 API 进程和 Worker 进程都会立即开始采集该模块的 `DEBUG` 日志。
3. **15 分钟自动到期**：为了防止管理员忘记关开关导致磁盘和数据库被打满，临时 DEBUG 采集会在 **15 分钟后自动关闭**；问题排查完后，你也可以随时手动提前关闭。

## 三、在线保留条数与服务器文件落盘

管理员可以在页面上一键切换 **“服务器文件记录”** 开关（该设置持久化保存在数据库中，服务重启后依然生效）：

| 服务器文件记录开关 | 数据库在线运行日志保留上限 | 服务器本地 `.log` 文件 |
| :--- | :--- | :--- |
| **关闭（初始默认）** | 保留最近 **20,000 条** （不按 7 天时间清理） | **不新建、不追加写入任何文件** |
| **开启** | 最多保留 **100,000 条**，且不超过 **最近 7 天** | 写入 `LOG_STORAGE_DIR`，单文件最大 **10 MiB**，最多保留 **5 个轮转文件** |

### 存储与轮转细节说明
- **关掉文件开关后历史数据怎么办？** 即使保持默认的“关闭文件记录”，最近 20,000 条运行日志依然保存在 PostgreSQL 数据库里，重启服务不会丢失。如果从“开启”切回“关闭”，数据库里的在线运行日志会自动裁剪保留最近 20,000 条，而磁盘上之前已经生成的 `.log` 文件会原样保留在目录里（不会自动删文件，但再次开启时也不会把旧文件里的内容导回数据库）。
- **操作审计永不按此规则清理**：操作审计（Audit Logs）与运行日志分表独立存储，**不受** 上述 20,000 / 100,000 条或 7 天的自动清理限制，长期保留供安全追溯。
- **文件目录配置**：服务器日志文件路径由 `backend/.env` 中的 `LOG_STORAGE_DIR` 指定（默认 `../.local/logs`）。API、Worker 和 CLI 进程必须指向同一个可写目录；多进程同时写文件时通过数据库锁协调顺序（如果是多台服务器集群部署，需将该目录挂载到共享文件系统）。

## 四、导出下载与安全脱敏红线

### 1. 导出 `.log` 文件
点击页面上的 **“下载日志”** 按钮，会将当前视图（运行日志或操作审计）在当前筛选条件下的记录导出为标准 UTF-8 `.log` 文本文件（无论“服务器文件记录”开关是否开启均可下载）。
- **单次导出上限为 10,000 条**：如果当前筛选条件下超过 10,000 条，系统会明确提示你先缩小时间范围或加上模块/关键词过滤，**绝不会静默截断只给你下载前一半数据**。
- 修改文件开关、开启临时 DEBUG 以及下载日志文件这三类操作本身，也都会自动记入操作审计。

### 2. 敏感信息零记录红线
为了保护师生隐私与考试公平，日志系统从底层实现了严格的脱敏隔离：
- **绝不记录**：用户明文密码、JWT / Session 令牌、Cookie、数据库连接串、完整的 HTTP 请求正文、学生的作答内容、未公布的标准答案与解析。
- **异常栈脱敏**：捕获未预期异常时，不会把包含敏感数据的函数局部变量转储到日志里。
- **审计摘要脱敏**：管理员在日志页查看操作审计时，页面只展示安全摘要，不会直接暴露用户的私密联系方式、答案正文或完整修改前后快照。

## 五、开发者维护与自检说明

1. **怎么验证日志链路是否正常工作？**
   在 `backend/` 目录下运行内置的自检命令：
   ```bash
   uv run python -m app.cli logging-check --module cli --count 1
   ```
   该命令会发送一条固定的安全诊断日志，随后你可以在管理后台“系统日志”页面筛选 `cli` 模块，确认能否实时刷出该记录（请勿在正式业务环境把 `--count` 设得很大，以免冲掉有用的历史运行日志）。
2. **如何在新代码里打日志？**
   - 运行日志使用独立事务与有界缓冲（单进程队列上限 5000 条，每批最多写入 200 条）。如果遇到极端数据库故障导致缓冲队列满了，溢出的诊断日志会被安全丢弃并在恢复后的下一批日志里记录丢弃条数，**绝不阻塞或回滚主业务请求**。
   - 业务开发新增日志采集点时，请传入稳定的模块名（`module`）、中文任务名（`task`）以及请求关联标识，只记录操作结果与业务对象 ID，切勿把用户输入的表单正文直接拼进日志字符串。
