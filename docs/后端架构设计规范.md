# 后端架构设计规范

版本：v1.0。确认及生效日期：2026-09-21。状态：用户已确认，作为后端新增开发、架构整改和代码评审的正式规范。

本规范对应[第一轮问题检查](./第一轮问题检查.md)。已有需求规格继续有效，架构调整不改变业务行为。规范生效不代表现有代码已完成整改，问题修复状态单独跟踪。

## 1. 架构原则

1. 三层：路由层、业务层、数据库 CRUD 层。
2. 按业务模块组织目录，例如 exam 内部包含自己的三层，不在全项目建立 routes/services/crud 三个大目录。
3. 使用 SQLModel／SQLAlchemy ORM 表达数据库访问，避免直接拼写原生 SQL。
4. 认证／会话妥善封装，接口输入、输出和错误契约明确；查询控制加载范围，避免隐式 N+1。

定位为借鉴 DDD 业务边界的模块化三层单体；不要求完整实现聚合根、仓储接口、领域事件总线等模式。模块按业务职责划分，不按学生／教师／管理员角色划分业务规则。

## 2. 分层职责

路由层负责 HTTP 请求处理。数据库事务由顶层业务用例控制，不交给每个路由或 CRUD 函数自行提交。

| 层 | 负责 | 不负责 |
|---|---|---|
| 路由层 | 路由注册、参数验证、依赖注入、身份取得、通用角色检查、CSRF、通用流控、Cookie／HTTP 响应 | SQL/ORM 查询、业务状态转换、拼 Redis key、数据库 commit |
| 业务层 | 用例编排、业务规则、资源级权限、状态转换、审计内容、数据库事务、跨模块协调及提交后失败策略 | 依赖 FastAPI Request/Response、直接执行数据库查询、返回 HTTPException |
| 数据库 CRUD 层 | ORM 查询和持久化、锁读取与刷新语义、聚合／分页／批量加载、必要的 flush | 判断“教师是否有业务权限”、决定审核结果、发送 Cookie、自行 commit、完整业务流程 |

通用身份／角色筛选可以放路由依赖；“教师是否关联当前班级”“申请能否重新提交”等资源与状态规则必须由业务层保证，确保 CLI／worker 复用时不会跳过。

### 应用用例编排归属

不单独建立 application 目录，多步业务用例编排统一归业务层。例如注册同时建立用户、资料、申请和审计，由业务层的一次 register_student 用例完成。

HTTP、CLI 和后台任务复用业务用例，保持状态转换、审计与事务规则一致；路由仅负责将请求映射为用例输入、将用例结果映射为 HTTP 响应。

## 3. 模块与目录规范

```text
backend/app/
  main.py
  core/
    config.py
    database.py
    redis.py
    errors.py
  modules/
    identity/
      router.py
      service.py
      crud.py
      models.py
      schemas.py
    auth/
      router.py
      service.py
      session_store.py
      password.py
      schemas.py
    teaching_class/
      router.py
      service.py
      crud.py
      models.py
      schemas.py
    exam/
      router.py
      service.py
      crud.py
      models.py
      schemas.py
  cli/
  workers/
```

以上结构作为模块组织基准，按实际业务需要创建文件，不提前创建空模块。初期使用函数或小类均可；模块增长后再按具体子业务拆分，不机械复制模板。auth 的 Redis 会话存储放 session_store，不伪装成关系数据库 CRUD。

core 仅保存技术基础设施，不演化为 shared/utils 业务规则堆积处。models 定义持久化实体，schemas 定义明确的数据契约；不用模型继承强行共用所有字段。

## 4. 依赖与跨模块调用

正常调用方向：入口 → 业务用例 → CRUD／会话存储 → PostgreSQL／Redis。

- HTTP、CLI、worker 作为不同入口调用同一业务能力。
- 路由不调用 CRUD，也不直接访问 ORM 表或 Redis 连接。
- CRUD 不依赖路由、HTTP schema 或业务 service，不反向抛 HTTP 错误。
- 业务模块访问其他模块时调用其公开业务能力／查询能力，不直接操作其内部 CRUD 或表。
- 跨模块组合操作由顶层业务用例协调；下级操作复用同一数据库 Session，不各自提交。避免用 HTTP 自调用实现模块协作。
- 依赖可由 FastAPI Depends 装配，但业务函数本身接收明确参数，不通过 Request.app.state 查找依赖。
- 不要求每个函数都建立接口类，不引入无实际用途的通用 BaseService/BaseCRUD。

## 5. 事务与异常

- 一次业务写操作的顶层用例拥有事务；业务数据与必要审计同事务提交。
- CRUD 可 add、delete、flush、获取锁，但不 commit；下级业务函数也不能暗中结束顶层事务。
- 明确顶层用例和可组合内部操作，避免多个 service 相互调用时产生嵌套提交；不依靠到处传 commit=true/false 管理事务。
- 认证依赖提前读取过数据库时，要处理 AsyncSession autobegin；不能在已有事务上机械套 begin。认证身份快照与写入事务的实时验证职责须分开。
- 关键写入锁定后按需刷新 ORM 对象，并重新检查状态／版本。with_for_update 不代表现有对象一定得到新属性。
- 业务错误以稳定 code 和必要上下文表达，在 HTTP 入口统一映射状态码；CLI／worker 按各自入口表达同一错误。
- 只把已识别的唯一约束冲突翻译为“账号已存在”，不将全部 IntegrityError 都转换为同一业务错误。
- 数据库提交成功后的 Redis 失败不得冒充数据库写入未发生；定义可重试、可观测的清理／补偿策略。策略需单独落实，不能只写 catch 后忽略。
- 刷新凭据轮换属于完整业务能力，统一处理前置检查、原子消费、版本校验及交付失败语义。

## 6. ORM 与查询

- CRUD 内使用 ORM 实体及 SQLAlchemy 表达式，包括 select、join、func.count、update、delete 和 with_for_update。这些不是拼接原生 SQL。
- 路由和业务层不接触具体 SQL 查询；业务层提供查询意图和过滤参数。
- 列表与详情使用不同查询，列表先分页、聚合和批量加载，按需使用 selectinload 等加载策略；不为了统一序列化而加载全部关联。
- 响应映射不执行查询，不依赖异步 lazy loading。查询次数与数据加载成本应可推断。
- 原生 SQL 仅在迁移或 ORM 无法合理表达的 PostgreSQL 特性等场景单独说明原因；禁止字符串拼接用户输入。Redis Lua 不属于关系数据库 SQL，应封装于会话存储模块。

## 7. 接口契约与验证

- 请求／响应模型明确声明，不直接返回 ORM 行；避免统一成无约束 dict[str, Any]。
- 业务层不返回 Response 或设置 Cookie；可以返回有类型的业务结果，由路由映射响应。
- 保留真实 PostgreSQL／Redis API 集成测试和少量浏览器流程。架构整改不以大量内部 mock 测试替换既有行为验收。
- 增补提交后 Redis 故障、刷新中途数据库故障、并发改密及响应字段白名单等针对性验证。
- 代码评审必须检查依赖方向；需要自动化约束时可增加轻量静态导入检查，不强制引入额外架构框架。

## 8. 执行与验收

- 新增后端功能必须遵守本规范；现有实现按第一轮问题清单逐项迁移，尚未迁移的代码不作为新功能延续旧结构的依据。
- 整改以完整业务用例为单位，同时调整入口、业务逻辑、CRUD、异常映射和对应验证，避免仅移动文件而保留原有职责混杂。
- 代码评审检查分层依赖、事务所有权、资源级权限、响应契约、ORM 加载策略以及提交后失败语义。
- 每项整改记录实现提交、针对性测试结果及剩余限制；未完成验证的问题不得标记已修复。
- 本次仅将架构规范正式化，业务代码重构与第一轮问题修复尚未开始。
