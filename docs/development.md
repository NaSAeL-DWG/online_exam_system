# 架构设计与开发规范

本文档面向参与本项目开发的工程师，用最直白的语言讲清楚：**代码目录怎么分、后端三层架构有什么铁律、接口与安全怎么约定、前端状态怎么管，以及改代码的规范流程**。

动手写代码前，强烈建议先花 5 分钟读完 **[核心业务术语词典 (`../CONTEXT.md`)](../CONTEXT.md)** 和 **[三端角色操作指南 (`user-guide.md`)](user-guide.md)**，牢记三条核心业务铁律：
1. **试卷可复用，但创建考试时立刻深拷贝生成独立的“考试快照”**，互不污染。
2. **学生作答按次独立保存，最终成绩严格取“最后一次有效提交”**（若最后一次还没判完，最终成绩就是“待批改”，绝不用旧成绩顶替）。
3. **“发布考试”（让学生能考）与“公布结果”（让学生能查分）是两个完全独立的操作**。

## 一、前后端工程目录全景

系统采用**按业务领域划分的三层模块化单体后端 + Vue 3 前后端分离架构**：

```text
backend/app/
  core/                    全局配置、数据库连接生命周期、统一错误码与中文表单校验转换
  modules/<业务模块>/       每个业务领域独立一个文件夹，内含 router / service / crud / models / schemas
  cli.py                   命令行运维入口（管理员初始化、密码重置、会话清理补偿、日志自检）
  workers/                 ARQ 异步 Worker 入口（超时收卷、客观题自动判分、主观题均分派单与故障恢复）
backend/migrations/        Alembic 数据库迁移脚本（按 0001 ~ 0018 递增）
backend/tests/             基于真实 PostgreSQL / Redis 的 HTTP 集成测试与少量纯函数判分测试

frontend/src/
  api/                     强类型 HTTP 接口封装、CSRF 自动注入、跨标签页 Token 刷新协调、字段错误映射
  features/                按业务领域组织的状态管理、复杂局部组件与组合式逻辑（如作答租约、阅卷工作台、图表）
  views/                   路由级页面视图与用户任务编排
  components/              全站复用的纯 UI 基础组件（PageHeader、SurfacePanel、AppSelect、LoadingSkeleton 等）
  styles/ & design/        C3 设计系统 Token 变量（tokens.css）、Naive UI 主题配置（theme.ts）与全局布局样式
  router.ts & navigation/  路由表、角色守卫与侧边栏导航分组声明
```

## 二、后端架构设计铁律

### 1. 严格的三层职责边界（`router → service → crud`）

后端每个业务模块都遵循清晰的三层划分，**严禁跨层越权操作**：

| 层级 | 该干什么 | 绝对禁止干什么 |
| :--- | :--- | :--- |
| **路由层 (`router`)** | 解析请求参数、挂载身份认证与通用角色依赖、校验 CSRF、返回响应模型、读写 Cookie | **禁止**直接写 ORM 查询，**禁止**直接 `commit` 事务 |
| **业务层 (`service`)** | 校验具体资源权限、控制业务状态流转、记录安全审计、编排跨模块调用、**掌管顶层数据库事务** | **禁止**依赖 FastAPI 的 `Request`/`Response` 对象，**禁止**直接手写底层 SQL 拼接 |
| **数据层 (`crud`)** | 组装 SQLAlchemy/SQLModel 查询、分页、聚合、加行级锁（`with_for_update`）与 `flush` | **禁止**做业务权限判断，**禁止**在 CRUD 里擅自调用 `commit` |

- **一套业务逻辑多处复用**：HTTP 接口、CLI 运维命令和后台 ARQ Worker 统一调用 `service` 层公开的业务函数，不要在 Worker 或 CLI 里把业务逻辑重写一遍。
- **跨模块协作靠公开接口**：模块 A 需要模块 B 的数据或能力时，必须调用模块 B 公开的 `service` 或只读查询接口，**禁止直接 import 其他模块的内部表或 CRUD**。
- **拒绝过度抽象**：保持代码直白可读，不需要为每个函数套一层空壳 Interface 接口类，也不要搞大而全的 `BaseService`。

### 2. 事务管理与并发锁规约

- **一个写操作用例 = 一次顶层事务**：事务统一由最外层的 `service` 用例负责提交（`commit`）。被调用的下级组合函数只能 `flush`，**绝不能暗中提前 `commit`**，确保业务数据变更与操作审计同生共死。
- **加锁后必须刷新实体状态**：在并发场景下使用 `with_for_update` 锁住数据库行后，注意 SQLAlchemy 会话里如果此前已经加载过该对象，内存里的旧属性可能还没更新——需配合 `populate_existing` 或按需刷新实体，拿到数据库里的最新状态和版本号后再做业务判断。
- **按需加载，拒绝 N+1 与过度预加载**：列表接口只查列表需要的字段与聚合统计，详情接口才加载完整子项（例如考试列表绝不能一次性把所有历史答卷和答案全预加载出来）。优先使用 SQLAlchemy 表达式与 ORM，原生 SQL 仅限 Alembic 迁移或确实无法用 ORM 表达的 PostgreSQL 专属特性。

### 3. 错误处理与异步故障补偿

- **稳定的业务错误码**：业务异常统一抛出带稳定英文 `code` 的自定义错误，在 HTTP 入口统一映射为对应的 HTTP 状态码。
- **主库提交成功后，绝不因队列/缓存抖动报错回滚**：
  - 比如学生交卷已经成功写入 PostgreSQL，但往 Redis 投递判分消息时网络闪断——此时接口必须正常返回交卷成功，落库的持久化待办标记会由 Worker 定时扫描自动补判，**绝不能把入队失败包装成 500 交卷失败骗用户重交**。
  - 同理，修改密码或停用账号落库成功后，如果清理 Redis 旧会话暂时失败，通过持久化补偿表异步重试（返回 `X-Session-Cleanup: pending` 响应头），同时数据库里的 `auth_version` 版本号会立即在鉴权时拦截旧会话。

### 4. 日志与审计双轨制

- **运行日志（Runtime Logs）**：通过统一标准 `logging` 采集，采用进程内有界内存队列（上限 5000 条）+ **独立数据库事务**异步批量落库。哪怕日志写入失败，也绝不会导致正常业务事务回滚。
- **业务操作审计（Audit Logs）**：涉及账号、权限、考试发布、成绩公布/撤回、改分等关键动作的审计记录，继续**与业务事务绑在一起原子提交**，并通过身份模块公开的脱敏查询接口供管理员审阅。
- **注意累加式日志筛选规则**：日志模块的等级筛选采用项目特定的累加规则（详见 **[系统日志文档](logging.md)**），开发或维护时切勿套用常规的“按最低严重级别过滤”。

## 三、接口契约、认证安全与敏感数据边界

1. **接口规范与金额/分值精度**
   - 启动后端后访问 `/docs` 或 `/openapi.json` 查看实时契约。
   - 分页列表统一接收 `page`（默认 1）、`page_size`（默认 20，最大 100）和可选搜索词 `q`，统一返回 `{ items, total, page, page_size }`。
   - **所有题目分值、得分与比率在 JSON 中一律使用十进制字符串传输，后端一律使用 `Decimal` 计算**，杜绝浮点数精度丢失。
2. **HttpOnly Cookie + CSRF + 单次 Refresh Token**
   - 登录凭证存放在 `HttpOnly` Cookie 中，前端 JS 不碰 Token，也不往 `localStorage` 里存任何认证凭据。
   - 客户端初始化时先调 `/api/auth/csrf` 获取 CSRF Token，后续所有写请求（POST/PUT/PATCH/DELETE）必须在请求头携带 `X-CSRF-Token`，服务端严格比对 Header 与 Cookie。
   - Refresh Token 采用单次轮换（CAS 原子替换）；前端通过 Web Locks 协调多标签页并发刷新，防止多个标签页同时拿旧 Token 刷新触发重放保护。
3. **敏感数据零泄露**
   - **严禁将明文密码、Token、Cookie、学生作答内容或未公布的标准答案打进日志**。
   - 学生端读取任何成绩、答卷回看、错题或学习分析时，后端每次都会重新校验“是否本人、是否有考试资格、考试是否已公布、是否开启回看”，**绝不能只靠前端隐藏按钮来做权限控制**。
   - 成绩响应与题目受保护图片一律加上 `Cache-Control: private, no-store`。如果老师中途撤回了成绩，前端即使收到此前发出的迟到响应，也会校验代次并丢弃，绝不把已撤回的旧分数重新渲染回页面上。
   - 题目上传的图片必须走后端鉴权 API 读取，严禁将图片上传目录直接作为公开静态资源暴露。

## 四、前端职责划分、视觉规范与表单体验

### 1. 代码分层与 C3 视觉复用
- **`views/` 编排流程，`features/` 收敛状态，`api/` 定义类型**：复杂的答题租约协调、阅卷状态管理、图表按需加载都封装在 `src/features/` 下，不要把几百行状态逻辑全塞进一个 `.vue` 页面文件里。
- **严格复用 C3 设计变量**：全站色彩与圆角定义在 `src/styles/tokens.css` 和 `src/design/theme.ts` 中（`#F6F7F9` 浅灰画布、`#FFFFFF` 纯白面板、`#2164CE` 清亮蓝主操作、零圆角直角侧栏）。写新页面时优先复用 `PageHeader`、`SurfacePanel`、`AppSelect`、`LoadingSkeleton` 等共享组件，不要硬编码旧版绿色或野生色值。

### 2. 界面层级与响应式要求
- **任务优先**：每个页面只有一个明确的 `h1` 主标题和最突出的当前核心操作。
- **状态分明**：清楚区分“加载中、空数据、请求报错、无权限不可操作”四种状态。如果写请求已经成功但随后的列表刷新失败，要明确告知“保存已成功，但刷新列表失败”，避免误导用户重复点击提交。危险操作（如取消考试、撤销资格、归档）必须弹窗说清操作对象、后果及是否可恢复。
- **桌面端优先 + 390px 窄屏适配**：在保证 1440px/1280px 桌面端体验的同时，所有页面、弹窗和操作栏必须在 390px 手机宽度下正常重排，严禁撑破页面出现整页横向滚动条（宽数据表格应在表格容器内部局部横向滚动）。所有输入框和按钮需具备清晰的语义标签与键盘焦点支持。图表模块（ECharts）按需加载，并始终提供可展开的数据表格和统计口径说明。

### 3. 中文就近表单校验与未保存防丢保护
- **前后端统一的中文就近报错**：前端先行拦截已知格式约束，错误提示紧贴在对应字段下方，自动绑定 `aria-invalid` / `aria-describedby` 并把焦点移到第一个出错的输入框。后端返回的 422 校验错误由 `core/validation_errors.py` 按错误类型统一转换为自然中文（保留点分隔的 `fields` 字段路径），再由前端 `api/fieldProblems.ts` 统一映射展示，**绝不把 Pydantic 原始英文报错直接甩给用户**。
- **未保存内容离开拦截**：在题目编辑、组卷、考试配置、阅卷打分、错题笔记等表单中，只要有未保存的改动，无论是切换路由、关闭弹窗还是刷新浏览器，都必须提示用户确认。但要注意两个安全例外：**当登录会话失效或成绩被老师撤回失去查看权限时，必须立即退出或清空敏感内容，不能被“未保存提示”卡住**。

## 五、标准开发与提交流程

每次开发新功能或修复问题，请按以下 5 步走完闭环：

1. **先写失败测试（TDD）**：在公开的 HTTP API 或真实浏览器 E2E 边界上，先写一个能复现问题或检验新需求的失败测试用例。
2. **最小化实现并跑通**：编写结构清晰、注释到位的实现代码（后端接口函数需写中文文档注释，复杂的并发锁、事务和可见性判断需注释说明“为什么这么写”），跑通刚才的测试。
3. **自检与定向回归**：检查代码分层是否越界、权限是否闭环、UI 在桌面和 390px 下是否正常；根据你的改动范围，挑选相关的集成测试和构建检查跑一遍（具体命令见 **[测试与验证指南](testing.md)**）。
4. **同步更新文档**：如果你的改动影响了使用方式、配置项或架构约定，及时同步更新 `docs/` 下的对应文档（本地过程草稿放在不入库的 `tech-docs/`）。
5. **干净地提交与推送**：使用约定式提交格式（如 `feat(exam): ...`、`fix(ui): ...`、`docs: ...`）提交代码并推送到远端。提交前务必检查 `git status` 和 `git diff`，**绝不把 `.env` 密钥、`.local/` 运行产物、数据库文件或临时截图混入 Git 仓库**。
