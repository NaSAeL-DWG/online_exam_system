# 开发与架构

## 业务边界

系统是按业务模块组织的三层单体，HTTP API 与 Vue 前端分离。先阅读[领域术语](../CONTEXT.md)和[角色操作指南](user-guide.md)：试卷可复用，考试建立独立快照；作答按次保存，最终成绩取最后一次有效提交；结果公布与考试发布分别控制。

```text
backend/app/
  core/                    配置、连接生命周期、通用错误与技术契约
  modules/<业务模块>/       router、service、crud、models、schemas
  cli.py                   管理员初始化、重置与会话清理入口
  workers/                 到期提交、判分、分配与恢复入口
backend/migrations/        Alembic 版本迁移
backend/tests/             真实 HTTP 集成与少量判分规则测试
frontend/src/
  api/                     类型化 API 调用
  features/                按业务功能组织的状态、组件与操作
  views/                   页面及流程编排
  components/              共用组件
  styles/                  设计变量、基础组件、布局
  router.ts                路由及角色入口
```

## 后端分层

| 层 | 职责与约束 |
|---|---|
| 路由 | 参数、认证依赖、通用角色、CSRF、响应模型及 Cookie；不查询 ORM、不提交事务 |
| 业务 | 资源权限、状态转换、审计、跨模块用例及顶层事务；不依赖 Request/Response，不直接拼查询 |
| CRUD | ORM 查询、分页、聚合、锁与 flush；不决定业务权限，不 commit |

HTTP、CLI、worker 复用公开业务能力。跨模块通过公开业务／查询接口协作，不能直接操作其他模块的内部表和 CRUD。一个业务写用例拥有一次事务；下级可组合操作不能暗中提交。无需为每个函数建立接口类或通用 BaseService。

锁定后按需刷新 ORM 实体，再判断实时状态与版本；`with_for_update` 本身不能保证会话中的旧对象已更新。列表与详情分别控制加载范围，不为列表预加载全部历史答案。使用 SQLAlchemy 表达式和 ORM，原生 SQL 仅限迁移或有明确理由的 PostgreSQL 特性。

业务错误使用稳定 `code`，HTTP 入口映射为状态码。数据库提交成功后入队失败不能冒充写入失败：持久待办及扫描负责补偿。清理旧会话失败由持久补偿记录重试，身份实时状态和认证版本仍会拒绝旧会话。

## 接口与敏感数据

启动 API 后以 `/docs` 或 `/openapi.json` 查看准确契约；列表常用 `page`、`page_size`、`q`，响应提供 `items`、`total` 与分页信息。分值使用十进制字符串传输，计算使用 Decimal。

认证使用 HttpOnly Cookie。客户端先取得 `/api/auth/csrf`，写请求携带 `X-CSRF-Token`；Cookie 与 Header 必须一致。刷新凭据轮换，前端协调并发刷新。不得将密码、令牌或答卷放入日志。

学生的每次结果读取都校验本人、资格、考试状态及回看权限；不能仅隐藏前端按钮。成功结果与受限图片使用 `private, no-store`。撤回结果后，迟到的旧请求也不能重新显示页面上的旧成绩。图片必须走鉴权 API，不公开上传目录。

## 前端职责与样式

页面负责串联用户任务，业务状态和操作收敛在相应 feature，API 层表达响应类型。共用设计变量位于 `src/styles/tokens.css`，基础视觉与布局由其余 styles 和共享组件提供。新增界面优先复用语义一致的表单、状态与反馈组件。

页面标题、主动作与辅助说明按当前任务排优先级：例如登录页以“账号登录”为主标题。区分加载、空态、错误和不可操作原因；写入已成功但刷新失败时要准确提示，避免诱导重复提交。危险动作明确说明对象、后果和恢复可能性。

电脑端优先，同时检查 390 px 页面宽度、对话框和操作区。数据表需要时在局部滚动，不让整页被撑宽。按钮保留可理解名称，表单标签与控件关联，支持键盘焦点。图表模块按需加载，表格提供完整数据与统计口径。

表单在前端检查已知约束，错误紧邻字段，关联 `aria-invalid`／`aria-describedby` 并聚焦第一处错误；后端继续作最终校验。后端 422 由 `core/validation_errors.py` 按稳定错误类型生成中文原因，保持 `fields` 点分隔路径；前端 `api/fieldProblems.ts` 统一中文字段摘要与未知错误兜底，不把 Pydantic 英文诊断直接展示给使用者。身份规则和嵌套内容规则分别收敛在相应模块，不给每个页面重复写翻译表。

密码强度与确认密码匹配条是辅助反馈，不能擅自增加后端没有的字符组合限制。编辑表单需要保护未保存内容：路由离开、弹窗关闭及主动刷新应说明放弃后果；会话失效和结果授权变化必须按安全规则退出或清空。敏感结果自动重读时，只有确认同一对象仍可见才可恢复本页未保存的备注，不存入全局或持久缓存。

## 改动流程

1. 在已确认的公开测试边界上写一个失败场景。
2. 实现最小完整行为并运行该场景，按切片推进。
3. 审查职责、权限、注释与样式；运行变更相关回归。
4. 同步 `docs/` 中受影响的使用和开发说明；本地实施过程写入 `tech-docs/`。
5. 约定式提交并推送，不夹带凭据、缓存、数据库或与任务无关的用户文件。

接口函数应有中文注释，关键并发、事务和可见性逻辑说明原因。过时 TODO 应更新或移除，不用泛化防御代码隐藏不明确的约束。具体命令见[测试与验证](testing.md)。
